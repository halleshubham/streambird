# Backend (`src/`)

NestJS 10 + TypeORM on Postgres. Global prefix `/api` (only `/health` and the public permanent live link `GET /stream/:slug` are outside it; `app.setup.ts` excludes them from the prefix and `ServeStaticModule`'s `exclude` list in `app.module.ts` keeps the SPA fallback from swallowing `/stream/*`). Wiring: `src/main.ts` → `src/app.setup.ts` (`configureApp`: cookie-parser, legacy-host redirect, global `ValidationPipe({whitelist, transform, forbidNonWhitelisted})`, `AllExceptionsFilter`). The app is created with `rawBody: true` (Razorpay webhook HMAC needs the raw body). `AppModule` also serves the SPA from `dist-web/` (`ServeStaticModule`, SPA fallback). e2e tests boot the same `configureApp`.

## Go live now: `StreamsService.create`
1. `AccountsService.assertCanStartStream` (hours + grace) then `assertDestinationCount`.
2. Load the account's `PlatformConnection`s (422 if any is not theirs).
3. Save `LiveStream` (SCHEDULED), `StudioSessionsService.createForStream`.
4. `provision()`: `Promise.allSettled` of `provider.createBroadcast` per destination (failure → a FAILED destination row; none succeeded → stream FAILED + 422). Optional `RelayProvider.createLiveInput` (extra forward only). `MediaMtxService.registerForward(streamId, ingestUrls)` → `POST /v3/config/paths/add/<id>` with `{source:'publisher', runOnReady: <ffmpeg>, runOnReadyRestart:true}`; returns `whipUrl = MEDIAMTX_WHIP_BASE_URL/<id>/whip` or null (best-effort, never throws). Destinations READY→LIVE, stream LIVE, `startedAt` set.
5. The browser then mints a host token, connects the socket and publishes WHIP. The ffmpeg command (`buildRunOnReady`) pulls RTSP over loopback TCP with `-c:v copy -c:a aac` (WHIP audio is Opus; FLV cannot carry it) teed to every RTMP(S) URL. Only `rtmp(s)://` is accepted and every argument is shell-quoted (`shQuote`).

**Stale live streams** (`stale-stream-reaper.service.ts`, config `staleStreams.*`, env `STALE_STREAM_*`, see operations.md): a stream marked LIVE whose picture never arrived or froze is ended automatically. Every `STALE_STREAM_CHECK_SECONDS` it reads MediaMTX `listPathStats()` (ready + `inboundBytes`, or `bytesReceived` on older MediaMTX) for live streams that have a `whipUrl`: (1) **never published**: no publisher was ever ready `STALE_STREAM_NO_PUBLISHER_MINUTES` after going live -> `StreamsService.end(id, account, {reason, usageUntil: startedAt})` (bills no hours when the reaper watched it from the start; with no history after a backend restart it bills normally); (2) **frozen**: ready but the byte counter has not advanced for `STALE_STREAM_FROZEN_MINUTES` -> ended, billed up to the last moment data moved. A publisher that was seen and then vanished is NOT the reaper's: `GlitchRecoveryService` (slate, then its own end after 5 min) owns it. Never acts when MediaMTX is unreachable, on streams without a `whipUrl`, or when the byte counter is absent (warns once). `end()` takes `{reason, usageUntil}`: the reason is shown on the ended destinations' `errorMessage` ("Ended automatically: ..."). The web studio's host-socket-gone timer (studio-signaling.gateway.ts) never covered the Android app, which has no studio socket: this is the safety net for it. Tests: `stale-stream-reaper.service.spec.ts`, `test/e2e/stale-streams.e2e-spec.ts` (the harness sets `STALE_STREAM_AUTO_END=false` so its timer stays off; tests call `tick(now)`).

**Scheduled**: `StreamSchedulingService.schedule` stores a SCHEDULED stream (`isScheduledEvent`), PENDING destination placeholders, a studio session, a general link and emailed invites; `createOnPlatforms` pre-creates broadcasts (YouTube only, `canPrescheduleBroadcast`). Nothing is billed. **There is no cron/auto-start**: the host presses Start → `POST /streams/:id/start` → `StreamsService.start` re-checks limits, reuses pre-created broadcasts (`collectReusableBroadcasts`, unless complete/revoked/stopped/VOD), recreates destinations, `provision(…, reuse)`, `applyThumbnailToFreshBroadcasts`; on total failure it restores the snapshot and returns to SCHEDULED. `cancel()` emails guests and deletes platform broadcasts; `delete()` is silent.

**Thumbnails** (`stream_thumbnails`, one row per stream, `parseThumbnail` validates the bytes): `PUT/GET/DELETE /streams/:id/schedule/thumbnail` (scheduled streams only, returns `ScheduleDetail`) and the generic `PUT/GET/DELETE /streams/:id/thumbnail` (`setStreamThumbnail` etc., any SCHEDULED or LIVE stream of the account, returns `{hasThumbnail, thumbnailUpdatedAt, platformWarnings?}`; ended/failed -> 422). A 'go live now' stream has its broadcasts at create, so the create form uploads the thumbnail right after `POST /streams` (fire-and-forget, never delays the studio) and the upload pushes it to every destination broadcast through `StreamProvider.setBroadcastThumbnail`; platform refusals are warnings: **logged on the server** (`Thumbnail set on ...` / `Could not set the thumbnail on <platform> broadcast ...: <reason>`, so they show in the Coolify app logs) and, for go-live-now, handed to the studio via sessionStorage (`web-app/src/lib/thumbnailNotice.ts`) and shown as a dismissible `data-testid=thumbnail-notice` banner. YouTube = `thumbnails.set` (verified channel). Facebook = `POST /{live-video-id}/thumbnails` multipart `source` + `is_preferred=true` (`FacebookProvider.setBroadcastThumbnail`; Graph docs do not mention live videos on this edge, so best effort and **not verified against real Facebook**). Twitch has none.

**End** (`StreamsService.end`): `provider.endBroadcast` per live destination → `relay.deleteLiveInput` → `mediaMtx.removeForward` (stops the slate first) → revoke host tokens + invites → ENDED → `recordStreamUsage(hours)` (best-effort). **It always finishes**: each outside call is bounded by `withTimeout` (`common/with-timeout.ts`: 12 s per platform, 8 s relay/MediaMTX) and best-effort; a destination whose platform could not confirm the end is still marked ENDED with `errorMessage` set, and the failure is logged. This is what makes a superadmin's "Force end" of a stuck stream reliable (`POST superadmin/streams/:id/force-end`).

**Glitch recovery** (`GlitchRecoveryService`): polls `MediaMtxService.listPaths()` every 2 s; only UUID-named paths whose publisher was once ready. After 10 s with no publisher → `startSlate(streamId, dests, orientation)` on path `<id>-slate` (ffmpeg looping `glitch-slate[-portrait].mp4`); publisher back → `stopSlate` within ~2 s; after 5 min → `StreamsService.end`. State is in memory; `reconcile()` rebuilds it from MediaMTX after a restart. The studio gateway's 60 s host-disconnect auto-end skips streams being watched here. **Session limit**: `SessionLimitService` every 60 s ends LIVE streams over `maxSessionHours`.

## Account deletion (`src/account-deletion/`, migration 0030)
- **Code**: `AuthService.sendDeletionCode/checkDeletionCode` reuse `login_codes` under the key `delete:<email>` (a login code can never confirm a deletion and vice versa), emailed with `EmailService.sendAccountDeletionCode`. **Never skipped for review accounts.** Same 10 min TTL / 5 attempts. The code is *checked without consuming* first, consumed only after the 409 check and (company path) after the autopay cancel, so a refusal never wastes it.
- **Auth**: `AccountGuard` (cookie session + CSRF origin check). x-api-key callers get 403; pending-approval and suspended users are blocked by the guard (they email support). Superadmin, or an account that has a superadmin on it: 403.
- **Scope** (`scopeFor`): *company* = caller is the only `company_admin` on the account, or the only user on it; otherwise *member*. **member**: deletes only their own `users` row (sessions cascade) and their codes; the company's data stays. **company**: (1) 409 unless `confirmCompanyDeletion:true` when other users exist; (2) `BillingService.cancelAllForAccountDeletion` cancels every chargeable Razorpay subscription immediately (502 "nothing was deleted" on failure, code still valid); (3) consume code; (4) end LIVE streams (`StreamsService.end`) and cancel scheduled events (`StreamSchedulingService.cancel`, tells guests), best-effort; (5) `PlatformConnectionsService.revokeAllAtProvider` (Google token revoke, best-effort; Facebook/Twitch nothing to revoke); (6) one transaction: streams (cascades destinations, studio sessions, invites, tokens, thumbnails) -> connections -> brand kits -> assets -> presets -> subscriptions -> login codes -> users -> company -> account; (7) after commit delete R2 objects best-effort (`AssetsService.deleteStoredObjects`), audit row, notice emails.
- **Kept**: `payments` rows (amounts, Razorpay ids, no email/name; `user_id` set null). An account with any payment is **not** deleted but becomes an anonymous tombstone (`name='Deleted account'`, random key hash, no customer id, suspended, `accounts.deleted_at` set, migration 0030) because `payments.account_id` is NOT NULL ON DELETE CASCADE. Accounts without payments are deleted outright. Superadmin directory and analytics skip `deleted_at` rows.
- **Audit**: `AuditLogService.logAnonymous` (actor null, ids only): `account_delete_member`, `account_delete_company`, `account_delete_aborted`. Notices: `sendAccountDeletedNotice` to the caller and (company path) every member, no PII beyond the fact.
- **Preview** counts only. For a member everything except `memberCount` is empty/false/null.
- Tests: `account-deletion.service.spec.ts`, `test/e2e/account-deletion.e2e-spec.ts`, `migrations.e2e-spec.ts` (0030), `test/ui/account-deletion.spec.ts`. User docs: shackyapps-landing `docs-site/streambird/delete-account.md`.

## Support sessions (superadmin impersonation, migration 0036, `src/impersonation/`)
A superadmin can open a customer in **View as** (read-only) or **Act as** (may change configuration) mode. Security-sensitive: an authorised auth bypass, so everything is server-side and fail-secure.
- **Model**: table `impersonation_sessions` (admin_user_id, admin_session_id = the admin's own `user_sessions` row, target_user_id, target_account_id, mode `view|act`, reason <=200, started_at, expires_at = +30 min (`IMPERSONATION_TTL_MS`, not extendable), ended_at, end_reason `exit|replaced|expired|logout|target_gone|invalid`, ip_address, user_agent_hash, plus copies admin_email/target_email/target_account_name; the reference columns are `ON DELETE SET NULL`, never CASCADE, so history survives a customer deleting their account; `AccountDeletionService` ends the customer's open sessions, with an audit entry, before deleting). Partial unique index = one ACTIVE session per admin; starting another ends the old one (`replaced`). **No extra cookie**: the row, keyed by the admin's login session, is the only authority (a signed cookie would add a second thing to steal/forge and would also reach the admin's other browsers or the app). Another browser, the Android app or an API key of the same admin never impersonates; logout (`POST /auth/logout`) ends it.
- **Endpoints** (all `@Roles(SUPERADMIN)`): `POST /superadmin/impersonation {accountId | userId, mode, reason?}` (201, throttled 60/min/IP) returns `ImpersonationInfo` (mode, reason, startedAt, expiresAt, target{userId,email,displayName,accountId,accountName,companyName,suspended}); `GET` -> `{active:false}` or `{active:true,...info}`; `DELETE` (204, idempotent) = Exit. Refusals: target is a superadmin (403), yourself or your own account (400), unknown/deleted account (404), user still waiting for approval (409), **suspended account: `view` only** (`act` 409), both/neither of accountId/userId or a bad mode (400). An account opens as its company admin (else its first non-superadmin user).
- **Guard flow** (`AccountGuard`): approval/suspension/CSRF checks run against the REAL admin first. Then, only if the real user is a superadmin AND the route is NOT a `@Roles(SUPERADMIN)` route, `ImpersonationService.resolveForGuard(sessionId, admin)` looks for the unended, unexpired row for this login (expired/target gone/no longer superadmin: row ended, audit written, nothing changes). If found: view mode refuses every non-GET/HEAD/OPTIONS request (403 "View-only support session"); the **blocked list** refuses (below); an act session on a customer suspended meanwhile is refused; otherwise `request.user/account` = the TARGET, `request.actor` = the admin, `request.impersonation = {sessionId, mode, adminUserId, targetUserId, targetAccountId}`. Every downstream controller therefore keeps using `@CurrentAccount()` unchanged. **`/superadmin/*` always authenticates as the real admin** (so Exit, the banner and the admin tools work during a session, and a customer principal can never reach them); a test enforces that every `superadmin*` controller is `@Roles(SUPERADMIN)`. `SessionGuard` routes (`/auth/*`) always see the real person, except `GET /auth/me`, which returns the customer as `user`/`accountId` plus `impersonation` so the SPA renders as the customer (`needsPhone` forced false).
- **Blocked list (ONE place: `src/impersonation/blocked-when-impersonating.ts`)**: `@BlockedWhenImpersonating('<category>')` on a route or controller; categories and plain-language labels in `IMPERSONATION_BLOCK_CATEGORIES`; message = `Not allowed while acting as a customer: <label>` (403, both modes, any HTTP method). Marked: `billing` (POST billing/orders, verify, subscriptions, subscriptions/verify, subscription/cancel; reading subscription/payments/plans is allowed), `connections` (platform-connections connect/callback GET redirects, facebook/select, twitch/manual, DELETE :id), `go-live` (POST streams, streams/:id/start, studio-sessions/:id/host-token, presets/:id/start), `live-control` (POST streams/:id/end, destinations retry: anything that changes a running stream), `guest-email` (POST schedule/guests, guests/:inviteId/resend), `guest-link` (POST studio-sessions/:id/invites), `team-access` (team invite/remove), `customer-email` (POST account/delete/request). **Conditional guest emails** (`StreamSchedulingService`, flag `impersonating`): schedule with `guestEmails`, PATCH schedule when the stream has emailed guests and `notifyGuests !== false`, and cancel when it has emailed guests are refused with 403 `Guest invitations cannot be sent while acting as a customer`; scheduling without guests, editing with `notifyGuests:false` and deleting stay allowed. Customers have **no** password/email/API-key/MFA route (magic-code login) so there is no `credentials` category; `DELETE /account` needs the code emailed to the customer and is unchanged. Allowed by decision (act mode): brand kits/assets/ads/clock, kit-to-channel mapping, presets (not start), schedules without guest emails, thumbnails, revoking a guest link, studio layout, deletes of those. **Redaction** (`ImpersonationRedactionInterceptor`, global): while a support session is in effect every response, view or act, has any key matching `IMPERSONATION_REDACTED_KEY` (stream key, ingest/WHIP/RTMP urls, joinUrl/generalJoinUrl, invite/host tokens, `invitationText`) set to null, by key name over the whole JSON, so new DTO fields are covered. **No caching**: AccountGuard forces `Cache-Control: no-store` on everything in a support session (it wraps `res.setHeader`, so handlers cannot override). **Safety net = ALLOWLIST**: `test/e2e/impersonation.e2e-spec.ts` enumerates every controller route (via `ModulesContainer`) and fails for any non-GET route outside `@Roles(SUPERADMIN)` controllers that is not marked, not in `IMPERSONATION_EXEMPT_ROUTES` (public / own-login routes) and not in `IMPERSONATION_ACT_ALLOWED` (each with a reason); it also checks no stale entries, that go-live/live-control/guest markers stay, that OAuth connect/callback GETs are marked, and that every `superadmin*` controller is `@Roles(SUPERADMIN)`. **A new mutating endpoint fails CI until it is classified.**
- **Start/stop vs configuration (founder)**: starting AND stopping streams are blocked with `Starting and stopping streams is not allowed while acting as a customer` (`go-live`, `live-control`); server-side configuration of an existing stream stays allowed in act mode, also while it is LIVE (thumbnail, kit ads/clock/logo/wallpaper, schedule edits without guest emails, presets, kit-to-channel mapping; test "LIVE stream: act mode can still update..."). **Live studio controls (layout, ad show/hide/schedule per stream, ticker, lower thirds, clock, logo) are client-side state in the host's own browser; act mode changes them through the remote-control channel below (web studio only; the Android app is out of scope).**
- **Stale screens (`X-Support-Session`)**: the web client sends the active session id on EVERY request (`api/client.ts`). On a non-superadmin route, if the header is present and the admin has no ACTIVE session with that id (expired, ended in another tab, replaced, logged in as someone else), AccountGuard answers 409 `{code:'support_session_ended'}` (any method) instead of silently falling back to the admin's own account; the client clears state and returns to the admin area. Without the header (API clients, other tabs) an ended session simply means the admin is themselves again.
- **Audit** (`superadmin_audit_log`, target_type `account`, target_id = customer account, actor = the real admin): `impersonation_started` (strict: not written = no session), `impersonated_action` = the **intent**, written with `logStrict` and awaited BEFORE the handler of every act-mode mutating request (metadata phase `intent`, sessionId, mode, targetUserId/targetAccountId, method, route TEMPLATE like `/api/brand-kits/:id`, `resourceIds` = UUID route params only); **if it cannot be written the request is refused 503 "Audit log unavailable; action refused"** (fail closed); the same action name also records refused requests (status 403, `blocked` = `view-only|<category>|suspended`); `impersonated_action_result` (status, written after the handler, best-effort on purpose: the strict intent already proves the action was recorded); `impersonated_read` = each GET once per (session, method, route template) (in-memory dedupe, so a backend restart can log a route again); `impersonation_ended` (endReason, durationSeconds; actor null + adminEmail when the admin row is gone). **Never bodies, query strings, headers, tokens or non-UUID route params.** Expiry entries are written lazily and by the 60 s `sweepExpired` timer.
- **Sockets / emails**: the `/studio` gateway authenticates by host token or guest invite token, never the cookie, and the host token mint is blocked, so an impersonator cannot become the customer's host (the one extra door is the `support` role, below, which never yields publishing or a participant slot); viewing pages in view mode publishes nothing (a guest invite link is an ordinary guest path and is allowed). Support actions that email the customer or their guests are blocked (deletion code, team invite, payment/cancel, guest invitations: see above). `createOnPlatforms` on a schedule calls the customer's platform API with their stored token (creates a scheduled broadcast, not a public stream; founder allowed scheduling).
- **Live studio remote control (`src/studio/support/`, act mode only)**: a support session can attach a `support` socket to the `/studio` gateway of ONE LIVE stream of the customer and send a whitelist of picture-composition commands to the HOST studio. Silent by decision (no host-visible indicator; the audit log is the record); the host's own changes always win.
  - **Token**: `POST /streams/:id/support-control-token` (`SupportControlController`; in `IMPERSONATION_ACT_ALLOWED`, NOT blocked; `host-token` stays blocked). Works only with `request.impersonation` in ACT mode (view = 403 from the guard; customer/admin without a session = 403), stream of the impersonated account (else 404) and LIVE (else 409), support session re-checked in the DB (`ImpersonationService.checkControlSession`). Returns `{controlToken, expiresAt, studioSessionId}`; token = 32 random bytes, kept in memory as sha256 only (`SupportControlService`, restart drops them), bound to (stream, studio session, support session, admin), TTL = min(10 min, remaining session), re-mintable any time (the page mints again on every socket reconnect), revoked when the session ends. Written audit-first (strict). It is the ONE response allowed to carry it: `ReturnsSupportControlToken` makes the redaction interceptor spare top-level `controlToken` of that handler; everywhere else `control_?token` is redacted (`IMPERSONATION_REDACTED_KEY`). Never in audit metadata.
  - **Socket**: `auth {role:'support', sessionId (studio session), controlToken}`. Not in `socketState`, joins only room `support:<sessionId>` (never `session:<id>`), so it gets no `peer-joined`/`signal`/media, is no participant row, and no guest sees it; `signal`/`rtc-state` from or to it are dropped. On connect AND before every command (plus every 5 s and on the session-ended hook) the session must be active, unexpired, ACT, customer not suspended, stream LIVE, same admin/account; else `support:ended {reason}` then disconnect (100 ms linger so the last ack lands). Events: server to support `support:joined {streamId, hostConnected}`, `support:host {connected}`, `support:state {rev,state}`, `support:ack {id, ok, error?, appliedAt}`, `support:ended`; support to server `support:command {id,type,payload}` (socket.io ack = `{ok}` relayed / `{ok:false,error}` refused). Server to host: `support:command {id,type,payload,at,source:'support-session'}`, `support:state-request`. Host to server: `support:ack`, `support:state` (only accepted from a HOST socket of that session, <= 24 KB, relayed to the support room only, last one cached). A `support:command`/`support:ack`/`support:state` from any other socket (guest, host as sender of a command) is dropped: only the server relays.
  - **Whitelist** (`support/support-command.ts`, strict schema, unknown keys rejected, payload <= 1 KB, text <= 200): `layout.set {mode}`, `ads.manual {placement, manual: shown|hidden|null}`, `ads.enabled {placement, enabled}`, `ads.schedule {placement, mode, showSec, everySec}`, `ads.shrink {on}`, `kit.apply {kitId}` (must belong to the account, checked server- and host-side), `ticker.set {text?|null, on?}`, `lowerThird.set {name?, title?|null, show?}` (name = big line, title = small line), `clock.set {enabled?, position?, format?, showDate?, showSeconds?, timezone?, size?, style?, alternate?}`, `logo.set {position?, size?}`, `wallpaper.dim {n}`. EXCLUDED FOREVER: start/stop/go-live/end, publishing, resolution/bitrate, camera/mic/mute, screen share, guest admit/kick/mute, recording, invite creation, anything that changes who can join or what is published beyond that composition. Rate limit 20 per 10 s per support session; host answer timeout 8 s (`supportAckTimeoutMs`, overridable in tests) -> ack error.
  - **Conflict rule** (host side, `web-app/src/studio/supportControl.ts`): a command touching a setting the host changed in the last 3 s is refused with `host changed it just now`; a host change after a support command simply overrides it. No host socket: ack `The host studio is not connected`.
  - **Audit** (`superadmin_audit_log`, actor = admin, target = customer account; free text only as a LENGTH, never tokens): `impersonated_studio_control {event: token_minted|connected|disconnected, sessionId, streamId}` (mint/connect strict = fail closed) and `impersonated_studio_command` with `phase`: `intent` (STRICT, awaited before the host sees it; 503-style refusal `Audit log unavailable; command refused` if unwritable; `command`, `summary` <= 100 chars like `ticker.set{text[len=24],on=true}`, `commandId`, `streamId`), `result` (best-effort, `applied`, `error`), `rejected` (best-effort, error text). Tests: `src/studio/support/*.spec.ts`, `test/e2e/support-control.e2e-spec.ts`, `test/ui/support-control*.spec.ts`.
  - **Hardening (review of PR #95)**: (a) the ADMIN is re-checked wherever the session is (`ImpersonationService.checkControlSession`: mint, socket connect, EVERY command, the 5 s sweep): still a superadmin, user and account not suspended, and the login session row in `user_sessions` (`adminSessionId`) unrevoked and unexpired, else the row ends as `invalid` and the socket gets `support:ended`. Logout already ends the row (`auth.controller` logout is the only place that revokes `user_sessions`; there is no password / log-out-everywhere route, logins are magic codes); expiry of the login is caught by the re-check. (b) Host snapshots are untrusted: `support/support-state.ts` rebuilds them from a strict shape (malformed dropped, extra keys stripped), the server stamps its own monotonic `rev` per studio session (so a reloaded host restarting at 0 never looks older), coalesces to at most 5 relays/s (latest wins) and forgets the cached snapshot when the last host socket leaves. (c) `support:watching {on}` tells the host whether any support socket is attached; it publishes snapshots only then. (d) Max 3 support sockets per stream; a socket that dropped during the connect awaits is not registered; ghost entries are swept; the rate limiter entry is forgotten when the session ends. (e) `result` audit entries carry `hostReported:true` when the outcome came from the host (the strict `intent` entry is the trusted record; timeouts are server-generated). (f) A relayed command waiting more than 8 s (queue age in the host browser, or the server `at` stamp when the clocks are within 5 min) is dropped unapplied; `kit.apply` has a 10 s timeout so a hung download cannot stall the serial queue; the host re-validates enums, ranges and text lengths (defence in depth).
  - **Known limits (documented, accepted)**: the conflict window has blind spots: right after a support command (400 ms, first change per setting only) and during/after `kit.apply` (4 s, all kit-touched settings) a host change on those settings may be attributed to support and not block the next command. The control token is a bearer secret checked at connect time only (10 min, sha256 in memory); an open socket does not need it again, its authority is the live support-session re-check, so a stolen token is useless after the session ends and only usable by someone who can also complete the socket handshake while the session is active.
- **Phone remote control (Android app, `src/studio/support/phone-*.ts`)**: streams started from the Android app (1.0.14+) have a studio session but NO web host socket and no studio socket on the phone. While LIVE the phone long-polls the server with its normal cookie session (the stream OWNER's); the support page and socket are the same as for a web host. Protocol (exactly the one in streambird-android `docs/API-CONTRACT.md` / `FEATURES.md` section 27; routes in `PhoneRemoteController`, state in the in-memory `PhoneRemoteService`):
  - `GET /streams/:id/remote-control?after={seq}&wait=25`: `200 {commands:[{seq,id,type,payload,at(ISO)}], now(ISO)}` for commands with seq > after (strictly increasing, max 100 per answer); none pending = HELD up to `wait` (default and cap 25 s) then `204`; `404` not the caller's / unknown stream, `409` not LIVE (the channel is forgotten), `400` bad `after`/`wait`, `429` rate / hold caps. `POST .../ack` `{id, ok, error?(<=120), appliedAt?}` -> `204` always (ignored when the id is not pending for THAT stream: no replay, no cross-stream), `429` when acks exceed 40 per 10 s. `PUT .../state` `{rev, state}` -> `204`; `400` malformed, `413` body > 32 KB or state > 24 KB, `429` over 5 per second per stream. All answers `Cache-Control: no-store`.
  - **Security**: owner session only (the controller refuses `request.impersonation`/`actor` and API-key callers with 403, and the whole controller carries `@BlockedWhenImpersonating('phone-channel')`, a new category: AccountGuard answers 403 to ANY support session, view or act, any method incl. GET, before the handler runs; the 3 routes are therefore NOT in `IMPERSONATION_ACT_ALLOWED`, the safety-net test asserts the marker). Stream must be the caller's (404) and LIVE (409) on every call. The phone can never create commands: the queue only grows through `PhoneRemoteService.enqueue`, called from the gateway's support path after `parseSupportCommand`, the rate limit, the support-session re-check, the strict audit `intent` and the mapping. Poll answers contain only mapped, whitelisted commands.
  - **Caps**: one held poll per stream (a new poll supersedes the old one, which answers `204`), at most 10 held polls per account and 200 globally (`429`, the phone backs off), 40 polls per 10 s per stream, queue <= 200 pending per stream (support gets `Too many commands are waiting for the phone app`), a queued command expires after 2 min and is taken back out when the support path times out (8 s) or is answered, a client that hangs up frees its hold at once (`res` close).
  - **seq**: per-stream counter in memory, seeded when the channel is created (also at the first poll after a backend restart) with `max(Date.now() epoch ms, the phone's `after`)`, +1 per command, and raised to `after` whenever the phone is ahead, so it NEVER resets or goes lower during a live stream, restart included (the queue itself is lost on restart: an unacked command ends as "The phone app did not respond"). Epoch-ms values are ~1.8e12: the phone reads `seq` as a 64-bit `Long`. Single process (CLAUDE.md rule 9); no migration.
  - **Relay** (`StudioSignalingGateway.handleSupportCommand`): same validation, rate limit, kit check and strict audit `intent` as the web path. No web host socket AND a phone poll within the last 60 s (a held poll counts) = relay to the phone: `toPhoneCommand` then `PhoneRemoteService.enqueue`; the phone's ack (`onAck`) or the 8 s timeout completes the pending command (`support:ack` to the support socket, audit `result` with `hostReported:true` for the phone's answer, `false` for server-generated ones). A web host socket, when present, always wins (existing path unchanged). Commands the phone cannot do are answered by the server at once with `Not supported on the phone app` (intent + result audited, nothing queued). No host at all: `The host studio is not connected` (web wording) unless a phone ever polled this stream in this process, then `The phone app is not connected`; pending phone commands fail with that text when the phone goes quiet.
  - **Mapping** (pure, `phone-mapping.ts`, unit-tested in `phone-mapping.spec.ts`; the web page's `PHONE_SUPPORTED_COMMANDS` mirrors it):

| Support command (web whitelist) | Phone command | Notes |
|---|---|---|
| `ads.manual {placement, manual: shown\|hidden\|null}` | `ads.manual {placement, mode}` | `manual` renamed `mode` |
| `ads.enabled {placement, enabled}` | `ads.enabled {placement, on}` | `enabled` renamed `on` |
| `ads.schedule {placement, mode, showSec?, everySec?}` | same | passed through |
| `ads.shrink {on}` | same | |
| `ticker.set {text?\|null, on?}` | `ticker.set {text: string\|null, on: bool}` | non-empty text: `{text, on: on !== false}`; `''`/`null` text: `{text:null,on:false}` (clear); no text: `{text:null, on}` (`on:true` = show the phone's current text) |

| `layout.set`, `kit.apply`, `lowerThird.set`, `logo.set`, `wallpaper.dim` | not sent | server answers `Not supported on the phone app` |

  - **State** (`phoneStateToSnapshot`): the phone's `{v:1, platform:'android', appVersion, orientation, freePlan, ads{placement: {present,enabled,manual,mode,showSec,everySec,source}\|{present:false}}, adsShrink, ticker{text\|null,on}, clock{...}}` is rebuilt strictly (malformed = 400/dropped, unknown keys stripped, `appVersion` <= 20 chars `[0-9A-Za-z._+-]`) into the web snapshot shape (`layout:'phone'`, `adsPlan` free/custom from `freePlan`, ad `hasMedia = present`, `name` 'Kit ad'/'Phone ad', inert kits/lowerThird/logo/wallpaper placeholders) and re-validated by `sanitizeSupportState`; `platform:'android'` + `appVersion` are added by the SERVER only (a web host snapshot never carries them: `sanitizeSupportState` rebuilds without them). It goes through the SAME coalescing gate (<= 5 relays/s, latest wins), gets the server-stamped monotonic `rev`, is cached for late support sockets and is CLEARED (`support:host {connected:false, kind:'phone'}`) when the phone has not polled for 60 s (sweep every 5 s) or the stream is found not LIVE. `support:joined` now also carries `hostKind: 'web'|'phone'|null`, `support:host` carries `kind`.
  - **Audit**: nothing new in kind: `impersonated_studio_command` `intent` (strict, before relay), `result` (`applied`, `hostReported`, error), `rejected`; phone offline = `rejected` with the phone wording. Refused phone calls by a support session are logged by AccountGuard as impersonation `refused` entries (`blocked: phone-channel`).
  - **Review hardening (PR #96)**: (a) the controller registers `res.on('close')` BEFORE its two DB lookups and checks it right after, so a client that hangs up mid-lookup never takes a hold; per-account held cap stays 10 (= 5% of the 200 global cap, so no account can take more than 5%). (b) `after` > clock + 1e9 is 400 (cannot poison `seq`). (c) ack `appliedAt` is clamped to [now-5 min, now]; the phone's `error` loses control, bidi and other format characters (`\p{Cc}\p{Cf}\p{Zl}\p{Zp}`) before `support:ack` and the audit. (d) The id the PHONE sees is a server-generated uuid per relayed command (`PendingSupportCommand.phoneId`); support sockets keep their own client id for `support:ack`/audit, so two sockets reusing one id never collide. (e) A connected web host socket always wins: phone host events and phone state are ignored while `hostSocketIds(session)` is non-empty (pending phone commands still fail when the phone goes quiet). (f) Per-ACCOUNT request budget checked before any DB read (`PhoneRemoteService.allowAccount`): 240 polls, 120 acks, 120 state PUTs per minute -> 429 (a normal phone polls ~2.4/min, up to ~2/s while commands flow). No per-IP `@Throttle`: carrier NAT shares IPs between phones. (g) Decision: the routes are account-scoped, not user-scoped; any signed-in member of the owning account (team) could poll or ack. Accepted.

Review accounts and invited team members are auto-approved and get no such email.

## Approval digest (`superadmin/approval-digest.service.ts`)
Every `APPROVAL_DIGEST_INTERVAL_HOURS` (default 12, `0` = off) the **configured superadmin** (`SUPERADMIN_EMAIL`) gets ONE email (`EmailService.sendPendingApprovalsDigest`, template `email/approval-digest.template.ts`, HTML escaped) listing everyone in `UsersService.listPendingApprovals()`; **nothing is sent while none are waiting**. A check runs 30 s after boot and every 15 min. When the last digest went out is stored in `app_settings` (`approval_digest_last_sent`), claimed with one conditional upsert *before* sending (so overlapping processes during a deploy cannot double-send) and released if the send fails. `run({ now, intervalHours })` is public for tests; the e2e harness sets the interval to 0 so timers stay off.

## Auth and access
- **Session cookie** `sb_session`: httpOnly, `sameSite=lax`, `secure` when `NODE_ENV=production`, 30 days; random 32-byte token stored as sha256 in `user_sessions`.
- **`AccountGuard`** (`common/guards/account.guard.ts`) is on every resource controller. Order: (1) `x-api-key` → account by hash (CSRF skipped, no `request.user`); else (2) cookie session; (3) **approval gate** — any non-superadmin without `approvedAt` gets 403 (kept in the guard so new routes can't forget it); (4) account/user suspension; (5) **CSRF/origin check** on non-GET: `Origin` must be `PUBLIC_BASE_URL` or a `LEGACY_HOSTS` origin. (6) **support session** (superadmin only, see "Support sessions"): may swap the principal to the customer, after the checks above ran against the real admin. `SessionGuard` (cookie only, no approval check, NEVER impersonates) is only for `/auth/me`, `PATCH /auth/me/phone` and `/auth/logout` so pending users can see their status.
  - **Mobile number** (migration 0020): `users.phone` (E.164 via `common/phone.util.ts`, bare 10-digit Indian numbers get +91) and `users.phone_required` (true only for accounts created after 0020, via `UsersService` create sites; false for review accounts, superadmins and everyone older). `/auth/me` returns `phone` and `needsPhone`; `ProtectedRoute` renders `PhoneStepPage` before the approval check. Shown to the superadmin in Approvals and the company Users table. UI-test fixture `/approve` clears `phone_required`, so `signIn` users skip the step; `pendingSignup` users do not.
- **`RolesGuard` + `@Roles()`** must come **after** `AccountGuard`; API-key callers have no user so they always fail `@Roles` routes.
- **Email code**: 6 digits, sha256-hashed, 10 min TTL, 5 attempts; `request-code` always answers 202 (never reveals whether an email exists). **Google/Facebook login**: random `state` in a short-lived cookie; provider email treated as verified; both go through `findOrCreateForEmail`.
- **Android Google sign-in**: `POST auth/google/mobile` `{idToken}` (Google ID token JWT from Credential Manager). `GoogleIdTokenService` verifies it locally: RS256 signature against Google's JWKS (`googleapis.com/oauth2/v3/certs`, cached by Cache-Control max-age; one refetch for an unknown `kid`, at most every 10 s), then `iss`, `exp` (60 s leeway), `aud` ∈ `google.clientId` + `google.androidClientIds` (`GOOGLE_ANDROID_CLIENT_IDS`), `sub`, `email`, `email_verified === true`. Then `loginWithGoogleProfile` (same as the web callback) and the same cookie + JSON as `verify-code`. 400 bad body, 401 generic `Invalid Google sign-in` for any token problem, 503 if Google's keys cannot be fetched and none are cached, 429 at 20/min per IP (AuthModule has its own `ThrottlerModule`, since it cannot import CommonModule). Test: `google-mobile-login.e2e-spec.ts` (stubs global `fetch` for the JWKS URL).
- **Android Google sign-in, browser fallback** (native Credential Manager can fail, e.g. SHA-1 not registered): the app opens `GET auth/google/app?challenge=<base64url(SHA-256(verifier))>` (strictly `^[A-Za-z0-9_-]{43}$`, else 400; 20/min per IP) in a Custom Tab. It behaves like `GET auth/google` (state cookie, `prompt=select_account`) plus a 10-min httpOnly `sb_google_app` cookie (path `/api/auth/google`, SameSite=Lax, Secure per `cookieSecure`) holding the challenge. It reuses the SAME redirect URI (`google.redirectUri` = `/api/auth/google/callback`), so **no new Google Cloud redirect URI**. In `google/callback`, if `sb_google_app` is present the web cookie is NOT set and there is no redirect to the SPA: the minted session is parked in `AppHandoffService` and the callback answers 200 HTML (`no-store`, inline CSS, no external assets) "Return to StreamBird" that navigates to `streambird://auth?code=<code>` and shows an "Open StreamBird" button. Any failure (state mismatch, Google error, unverified email, superadmin refusal) shows "Sign-in failed. ..." with `streambird://auth?error=google_failed` and no details. Pending approval is NOT a failure (the app shows its pending screen). Both cookies are cleared. Then `POST auth/google/app/redeem` `{code, verifier}` (verifier 43-128 chars of `[A-Za-z0-9-._~]`; 400 bad body, 401 generic `Invalid sign-in` for every failure, 20/min per IP) checks `base64url(SHA-256(verifier))` against the stored challenge (timing-safe), sets the session cookie via `setSessionCookie` and returns the `verify-code` JSON. `AppHandoffService`: in-memory Map keyed by sha256 of a random 32-byte code, TTL 120 s, **single use even when the verifier is wrong** (a wrong verifier burns the code, so no brute force), swept on access and by an unref'd interval, capped at 1000 entries (oldest evicted). **Single-process assumption** (rule 9): a restart or a second instance drops/misses pending handoffs. Security: a custom-scheme link (`streambird://`) can be intercepted by another app on the phone, so the one-time code alone is worthless: it is bound to a PKCE challenge only the real app knows, and the verifier never leaves the app until redeem. Tests: `app-handoff.service.spec.ts`, `google-app-handoff.e2e-spec.ts` (stubs global `fetch` for Google's token and userinfo URLs). No config/env change.
- **Superadmin**: magic-code, Google and Facebook paths **refuse** a superadmin (`rejectSuperadmin`). Login = `superadmin-login` (password → emails an OTP, sent by `sendCode` which is never skipped) then `superadmin-verify` (password + OTP). `SuperadminSeedService` creates/reconciles the user from env at every boot and never promotes an existing non-superadmin; it silently skips if either env var is missing.
- **Review accounts** (`users/review-accounts.ts`, reads `process.env` at call time): listed emails are auto-approved on first sign-in, moved to `REVIEW_ACCOUNT_PLAN` (default `pro`, no expiry, only while on free), **skip the emailed code** (typing the address signs in), never apply to a superadmin. List throwaway accounts only.
- **Studio tokens**: host token (`studio_host_tokens`, minted by an authenticated account, revoked on end) and guest invite token (optional password); neither uses the cookie. The `/studio` gateway has `cors:'*'`; authentication is the handshake `auth` payload (`{role:'host', sessionId, hostToken}` / `{role:'guest', token, password?}`). A guest invite password is also verifiable up front via `POST …/invites/:token/check-password`.
- **Facebook/Google OAuth state and Facebook page selections are kept in memory** → this assumes **one backend process**. Do not scale out without moving them (also glitch state, host-end timers).

## Conventions
- **Config**: `ConfigService.get('camelKey')` from `src/config/configuration.ts` — env vars are read **only** there (exceptions: `review-accounts.ts`, `main.ts` `PORT`, `migrate.ts` `DATABASE_URL`). A new setting = add to `configuration.ts` + `.env.example` + `operations.md`.
- **Migrations**: hand-written, numbered SQL in `migrations/` (next is `0037_…`). `src/config/migrate.ts` applies unapplied files in filename order, each in a transaction, tracked in `schema_migrations`; the Dockerfile CMD runs `npm run migrate:prod && node dist/main.js` so **every deploy migrates**. `synchronize` is false. A new entity needs: the migration **and** an entry in `database.module.ts`'s explicit entity list **and** `TypeOrmModule.forFeature`. Naming strategy is snake_case. Migrations must be idempotent-safe on existing data (test: `test/e2e/migrations.e2e-spec.ts`). Skill: `streambird-add-migration`.
- **DTOs**: class-validator/transformer; the global pipe **rejects unknown fields**, so every accepted field needs a decorator. UUID params use `ParseUUIDPipe`.
- **Errors**: throw Nest `HttpException` subclasses; `AllExceptionsFilter` returns `{statusCode, message, timestamp}`; non-HTTP errors become a logged generic 500.
- **HTTP out**: `@nestjs/axios` `HttpService` + `firstValueFrom` (exception: `TurnCredentialsService` uses `fetch`). **Secrets at rest**: `EncryptionService` for connection credentials; API keys, session tokens and OTPs only as sha256.
- **Logging**: `new Logger(Class.name)`; `warn` for best-effort failures.
- **Guards**: `AccountGuard` on every new resource controller. Public endpoints that check a secret must be `@Throttle`d (`ThrottlerGuard`).
- **Add a platform** (skill `streambird-add-platform`): `Platform` enum → implement `StreamProvider` (`createBroadcast`, `endBroadcast`, optional pre-schedule/thumbnail/status/viewer-count hooks) → register in `ProvidersModule` (providers list **and** the `STREAM_PROVIDERS` factory inject list) → connect flow in `PlatformConnectionsController/Service` → env block in `configuration.ts` → check DB CHECK constraints in migrations and `PLATFORM_LABELS` in `stream-scheduling.service.ts`. `StreamsService` must never branch on platform.

## YouTube specifics
Scope: `youtube.force-ssl` only (override `GOOGLE_YOUTUBE_SCOPE`); Google approved this exact scope — **do not widen it** (re-verification). Calls used: `liveBroadcasts` insert/bind/update/transition/delete/list, `liveStreams.insert`, `thumbnails.set` (needs a verified channel), `videos.list` (concurrent viewers), `channels.list?mine=true` (id + title only). No `videos.insert`: video travels over RTMP. The Connections page and `/privacy` disclose this wording; tests pin it (`youtube-scope.e2e-spec.ts`, UI smoke).

## Gotchas
- `MediaMtxService.registerForward` is best-effort: `whipUrl` can be null and the stream still goes LIVE — a MediaMTX outage degrades silently.
- `StreamsService.start()` rollback deletes and recreates destination placeholders; re-reading the stream without its relation is deliberate (avoids a NOT NULL violation).
- Payments: never trust client/webhook amounts (compare with the DB); keep `fulfill`'s claim-then-apply order; the webhook needs `rawBody`.
- The Cloudflare TURN API token never reaches a client (`TurnCredentialsService` mints short-lived credentials).
- `/auth/*` has no explicit throttle (the OTP has its own 5-attempt cap). Explicit `@Throttle`s: stream create/schedule/guest-email routes in `streams.controller.ts` and the two public studio routes.
- `AccountGuard`'s CSRF check relies on the browser sending `Origin`; `PUBLIC_BASE_URL` must equal the site origin exactly.

## Assets and brand kits (R2)
`src/assets/`: `Asset` (account-owned file metadata; bytes in object storage under `acct/<accountId>/assets/<assetId>`), `BrandKit` (logo/wallpaper from the library, logo position/size, lower-third look, `isDefault`, one default per account) and `platform_connections.brand_kit_id` (a YouTube channel / Facebook Page points at one kit; several can share a kit; null = the account default). Migrations 0022 (plan `asset_storage_mb`, `watermark`), 0023 (`assets`), 0024 (`brand_kits` + link). Files are **proxied through the backend** (upload multipart <= 8 MB, validated by magic bytes PNG/JPEG/WebP and <= 8192 px; **GIF87a/GIF89a is accepted for kind `logo` only** (size from the logical screen descriptor, bytes 6-9 LE; `parseImage(data, { allowGif })`; a GIF as wallpaper/background/other is a 400 "GIF images can only be used as a logo"; served as `image/gif`; no DB constraint covers `content_type`, so no migration); `GET /assets/:id/file` streams with a private cache), so the bucket stays private and needs no CORS. `ObjectStorage` (`OBJECT_STORAGE`): `R2ObjectStorage` when `R2_ACCOUNT_ID/ACCESS_KEY_ID/SECRET_ACCESS_KEY/BUCKET` are all set, `MemoryObjectStorage` outside production, `DisabledObjectStorage` in production without credentials (`GET /assets` says `enabled:false`). Gate: plan `assetStorageMb` > 0 (Free 0 = browser-only; a day pass adds none); quota = sum of `size_bytes`. A file used by a kit cannot be deleted (FK RESTRICT -> 409 with the kit names); deleting a kit sets its connections back to the default. Routes (all AccountGuard): `GET/POST /assets`, `GET /assets/:id/file`, `PATCH/DELETE /assets/:id`, `GET/POST /brand-kits`, `PATCH/DELETE /brand-kits/:id`, `PUT /brand-kits/connections/:connectionId`. Schedule thumbnails still live in Postgres (`stream_thumbnails`); moving them to R2 is not done. The host studio reads kits (see `studio.md`, "Brand kits in the studio"); the guest studio does not need them.

## Powered-by mark (Free)
`plans.watermark` (true for Free via migration 0022; a day pass turns it off in `computeLimits`). Studio: `studio/poweredBy.ts` draws a small pill with the logo and "Powered by StreamBird" bottom-right above the ticker (client-side, so it is not tamper-proof). Platforms: `StreamsService.platformDescription()` appends `Powered by StreamBird - https://streambird.app` (see `streams/powered-by.ts`) to the description sent to YouTube/Facebook for accounts whose plan shows the mark; never stored in the stream's own description.

## Registration switch (auto-approve)
`app_settings` key `auto_approve_registrations` (default off), read/written by `users/registration-settings.service.ts`. `UsersService.findOrCreateForEmail` and `createCompanyAdmin` set `approvedAt = now` (no `approvedById`) when it is on; invited team members were always auto-approved. Superadmin routes: `GET/PUT /superadmin/registration` (`{autoApprove, last24h, last7d, waiting}`; PUT is audited as `enable_auto_approve`/`disable_auto_approve`), `POST /superadmin/pending-approvals/approve-all` (emails each person, audited `approve_all_pending`). UI: the "Registration" card on `/admin` (Approvals) with a Manual review / Auto-approve switch ("paused" = manual review: nothing is rejected, people wait in the queue; people already approved are never affected). Turning it on does not approve the existing queue; use "Approve all waiting". UI/e2e tests that toggle it must switch it back off (state is in the shared test DB).

### Advertisements in brand kits (migration 0027)
- Asset kind **`ad`** (CHECK widened; PNG/JPG/WebP/GIF, <= 8 MB, <= 8192 px). GIF is accepted for kinds `logo` and `ad` only (`parseImage(..., { allowGif })`, message "GIF images can only be used as a logo or an ad").
- Table `brand_kit_ads` (`BrandKitAd`): `brand_kit_id` FK CASCADE, `placement` (`lower_third|side_third|full_screen`), `asset_id` FK **RESTRICT**, `enabled`, `mode` (`continuous|interval`), `show_sec` (1..3600), `every_sec` (1..86400, the HIDDEN time between showings), UNIQUE(kit, placement). `AssetsService.remove` checks ads too (409 "used by the brand kit ..."); `GET /assets` `usedBy` includes kits using the file as an ad.
- API: every kit in `GET/POST/PATCH /brand-kits` has `ads: [{placement, assetId, enabled, mode, showSec, everySec}]` (ordered lower_third, side_third, full_screen; continuous ads have null seconds). `POST`/`PATCH` accept `ads` with REPLACE-ALL semantics (omitted = unchanged, `[]` = none). Validation (`BrandKitsService.checkAds`): max 3, unique placement, assets owned by the account and of kind `ad`, interval needs both numbers, ranges as above. Plan gate: saving a non-empty `ads` needs a plan without the Powered-by mark (`getLimits().watermark === false`, so not Free; a day pass counts) -> 403 "Your own ads are on the paid plans..."; kits themselves still need `assetStorageMb > 0`. Clearing ads is always allowed. Account-default and connection assignment are untouched.
- Review hardening: `ads: null` on POST/PATCH is treated like an omitted `ads` (unchanged / none), never a 500. `PATCH /brand-kits/:id` runs inside one transaction that locks the kit row (`SELECT ... FOR UPDATE`), so concurrent saves of one kit serialize; Postgres FK violation 23503 (file deleted meanwhile) -> 400, unique 23505 -> 409; deleting an asset that a kit grabbed in the same instant -> 409 (not 500). A logo must be of kind `logo|other` and a wallpaper `wallpaper|background|other` (an `ad` file is refused, 400) so "GIF only for logo/ad" stays strict. After a plan downgrade, saved ads stay readable and can be cleared with `ads: []` (always allowed, frees the RESTRICT-locked file); other kit edits keep them; non-empty `ads` are 403 on a watermark plan.

### L-shaped ads (migration 0031) and the kit thumbnail (migration 0032) -- API contract for web and Android
- **`l_shape` placement**: `brand_kit_ads.placement` CHECK widened to `lower_third|side_third|full_screen|l_shape` (0031). Accepted in `ads` AND `adsPortrait` (same entry shape, asset kind `ad`); the list limit is now **4** (one per placement per orientation); returned in the fixed order lower_third, side_third, full_screen, l_shape. Replace-all as before: an old client that only knows three placements and sends its list back drops the frame (omitting `ads` keeps it). Same plan gate (403 on a plan with the Powered-by mark).
- **`thumbnailAssetId`** (0032, `brand_kits.thumbnail_asset_id UUID NULL REFERENCES assets ON DELETE SET NULL` + partial index) on `GET/POST/PATCH /brand-kits`: `undefined` = unchanged, `null` = clear. Validation (`BrandKitsService.checkThumbnail`, from stored metadata): a file of the account, `image/jpeg` or `image/png` (no GIF/WebP), `size_bytes` <= 2 MB (`MAX_THUMBNAIL_BYTES`), width >= 640 (`MIN_THUMBNAIL_WIDTH`) -> else 400. Any library kind qualifies; uploads for this slot use asset kind **`thumbnail`** (new in the CHECK; `AssetsService.upload` runs `parseThumbnail` first so the friendly stream-thumbnail errors apply). `GET /assets` `usedBy` and the delete-409 include it (the DB FK is only the safety net). One thumbnail per kit, shared by both orientations (vertical streams still use a 16:9 thumbnail).
- **Resolution** (`BrandKitsService.thumbnailForConnection(accountId, connectionKitId, override?)`; client mirror `web-app/src/lib/kitThumbnail.ts`): explicit per-stream thumbnail (`stream_thumbnails`) > override kit > the destination's kit (`platform_connections.brand_kit_id`) > the account default kit > none. A kit without a thumbnail gives none (NO fall-through to another kit). Never throws: an unreadable file is logged at warn and skipped. Per destination (provider API `setBroadcastThumbnail(conn, broadcastId, image)` is per destination), so destinations with different kits each get their own kit's image.
- **Wiring** (never blocks going live; failures are `logger.warn` + warnings): (1) go live now: `POST /streams` accepts `thumbnailBrandKitId` (omitted = automatic, a kit id = that kit, `null` = none) and, after the stream is live, `StreamsService.applyKitThumbnailsAfterCreate` sends each destination's kit thumbnail (10 s cap); the response carries `thumbnailKit {id,name}|null` and `thumbnailWarnings[]` (the web app hands the warnings to the studio's `thumbnail-notice`). The web client sends `thumbnailBrandKitId: null` when the host chose an own image (uploaded right after, so it lands last and wins) or "No brand kit". (2) scheduled with `createOnPlatforms`: `precreate()` applies explicit else the destination's kit thumbnail to the new broadcast. (3) scheduled, created at start: `applyThumbnailToFreshBroadcasts` does the same for broadcasts created by `start()` (platforms with `thumbnailAppliesWhenLive`). The kit thumbnail is NOT stored as the stream's own thumbnail (`hasThumbnail` stays false); the schedule/stream pages say "From brand kit X" (`KitThumbnailNote`).

### Brand kit orientation sets (migration 0028) -- API contract for web and Android
- A kit has a **landscape (16:9)** set and a **portrait (9:16)** set. Orientation words are the stream's (`LiveStream.orientation`: `landscape` | `portrait`). Migration 0028: `brand_kits.logo_asset_id_portrait`, `wallpaper_asset_id_portrait` (FK RESTRICT), `ads_shrink_picture BOOLEAN DEFAULT true`; `brand_kit_ads.orientation` (`landscape` default, CHECK) with UNIQUE(kit, orientation, placement) replacing UNIQUE(kit, placement). Existing rows ARE the landscape set.
- Response/request fields: landscape = the ORIGINAL names (`logoAssetId`, `wallpaperAssetId`, `ads`) so Android 0.3.x and old web keep working; portrait = `logoAssetIdPortrait`, `wallpaperAssetIdPortrait`, `adsPortrait` (same entry shape as `ads`, no `orientation` field inside entries). `adsShrinkPicture` (bool, default true). Shared by both sets: `logoPosition`, `logoSize`, `wallpaperDim`, `lowerThirdStyle`, `adsShrinkPicture`.
- Semantics: `ads` / `adsPortrait` are REPLACE-ALL per set (omitted or null = unchanged, `[]` = none); a client that only sends the landscape fields never touches the portrait set. Same validation, plan gate and 403/400 rules for both lists; the same asset may be used in both orientations. Portrait logo/wallpaper follow the logo/wallpaper kind rules. `AssetsService` `usedBy` and delete-409 include the portrait columns.
- **Which set a stream uses**: landscape stream -> landscape set. Portrait stream -> portrait set; logo falls back to the landscape logo when no portrait logo; wallpaper and ads do NOT fall back (absent). Implemented in `web-app/src/studio/brandKitSet.ts` `kitSetFor`.
- Suggested sizes/limits (one shared module, `web-app/src/studio/brandSizes.ts`, derived from `adRect`): logo 512x512 (<=1024), wallpaper 1920x1080 / 1080x1920, lower third 1280x240 (16:3) / 1080x360 (3:1; band is up to 1080x640), left third 640x1080 / 360x1920, full screen 1920x1080 / 1080x1920; files <= 8 MB, <= 8192 px, GIF for logo/ads only; shape warning when ratio is off by more than 1.5x (non-blocking).
- Facebook connect diagnostics: when `/me/accounts` returns no Pages the callback also calls `GET /me/permissions` and logs granted/declined permission NAMES at warn (`facebook-permissions.ts`, never the token).

### Brand kit default title and description (migration 0033)
- `brand_kits.title` (varchar 200) and `description` (text), both nullable; limits mirror a stream's own (`CreateStreamDto`: title 200, description 5000). `GET/POST/PATCH /brand-kits` return `title`/`description` (null when unset); omitted on PATCH = unchanged, `null` or blank = cleared, always trimmed (DTO `@Transform`); too long / not text = 400 with a plain sentence.
- Meaning: DEFAULTS for streams using the kit. `StreamsService.resolveText` (used by `POST /streams`, `POST /streams/schedule`, `POST /presets/:id/start`): an explicit title/description in the request wins (trimmed); a blank/omitted one takes the kit's, chosen by `src/assets/kit-text.ts` `pickKitText`: walk the destinations IN REQUEST ORDER, resolve each one's kit like the thumbnail (explicit `thumbnailBrandKitId` kit id; `null` = no kit; else the destination's kit; else the account default kit) and take the FIRST non-empty value, title and description independently. The kit choice is the existing `thumbnailBrandKitId` of `POST /streams` (no new request field); schedule has no override (automatic). Title is now optional on create/schedule: no title and no kit title = 400 "A title is required." (a preset start falls back to the preset name last). Text is COPIED onto the stream; later kit edits never change existing streams.
- Create/schedule responses add `titleFromKit`, `descriptionFromKit` (booleans) and `titleKit`, `descriptionKit` (`{id,name}|null`); GET of a stream/schedule does not carry them.
- A preset start now also passes the preset's kit choice (`brandKitId`: id / `null` = none / omitted = automatic) as `thumbnailBrandKitId`, so the kit thumbnail and text follow the preset's kit.
- Web: `lib/kitText.ts` mirrors the rule; Brand editor test ids `kit-text`, `kit-title-count`, `kit-description-count` (labels "Default title" / "Default description"); the new-stream form prefills Title/Description while untouched, hints `title-kit-note` / `description-kit-note` ("From brand kit X ..."). Tests: `test/ui/kit-text.spec.ts`, `test/e2e/brand-kit-text.e2e-spec.ts`, `src/assets/kit-text.spec.ts`.

### Brand kit clock: on-air date and time (migrations 0034, 0035)
- Nine columns on `brand_kits`, shared by the 16:9 and 9:16 sets (like `logoPosition`), always returned by `GET/POST/PATCH /brand-kits`, omitted on PATCH = unchanged: `clockEnabled` bool (default false), `clockPosition` `top_left|top_right|bottom_left|bottom_right` (default `top_right`), `clockFormat` `12h|24h` (`12h`), `clockShowDate` bool (true), `clockShowSeconds` bool (false), `clockTimezone` IANA name or null = the streamer's device zone (null; max 64; validated with `Intl.DateTimeFormat` in `isKnownTimeZone`, DTO `IsTimeZoneName`; blank string = null), `clockSize` `small|medium|large` (`small` since 0035; kits made before keep what they stored), `clockStyle` `text|pill` (`text` = compact plain text with a shadow, no box, under the logo; `pill` = the dark rounded plate of the first release; column `clock_style` varchar(8) + CHECK), `clockAlternate` bool (`true` = the time and the date take turns in one spot; `false` = both on one line; moot while `clockShowDate` is false). Migration 0035 adds `clock_style` / `clock_alternate` with those defaults and changes only the column DEFAULT of `clock_size`; DTO/service defaults for new kits match. Bad value = 400 with a plain sentence ("The clock position must be ..."). DB CHECKs mirror the enums. No plan gate beyond kits themselves. The studio draws it (`studio.md` "Clock"). The Android app is built against exactly these names: do not rename. Tests: `src/assets/dto/brand-kit.dto.spec.ts`, `assets.e2e-spec.ts` ("brand kit clock"), `migrations.e2e-spec.ts` (0034, 0035).
